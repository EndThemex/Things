# 元件库存管理系统 — 实施方案

> 版本：v1.0 ｜ 日期：2026-10-08 ｜ 定位：个人自用的元件（电子元器件/物料）库存与方案管理工具

---

## 1. 需求分析与细化

### 1.1 原始需求

1. 对元件进行管理，方便统计数量、类型，便于后续使用。
2. 元件字段：名称、类型、数量、规格、价格、颜色、购买链接、图片、备注、标签、修改时间。
3. 可创建「方案」（如：一个键盘方案需要哪些元件及数量），据此查看：
   - 当前剩余元件可制作多少份该方案；
   - 哪些元件需要补充、各需补充多少。

### 1.3 明确的假设（如与预期不符请指出）

1. **单用户系统**：仅自己使用，账号密码由服务端环境变量/配置文件预置，提供修改密码功能，不开放注册。
2. **数量为整数**：元件（电阻、轴体、螺丝等）按个/包计数，不做小数。
3. **图片**：每个元件 1 张主图（P1 扩展为多张），上传前前端压缩（长边 ≤1280px、JPEG 质量 0.8，兼顾手机拍照场景），存储在服务端 `uploads/` 目录，SQLite 存相对路径。
4. **价格**：数据库存储单价（元，两位小数），总价值 = Σ 数量 × 单价。录入/补货时提供两种方式：直接填单价，或填「数量 + 总价」由系统自动折算单价（总价 ÷ 数量，四舍五入到分）。补货时若填了总价，单价默认更新为本次采购价（最新价），不使用加权平均（个人使用，最新采购价更贴近补货成本）。
5. **类型**：用可管理的「分类」表（如：MCU、开关、电容、键帽…），支持自行增删，用于统计。
6. **标签**：自由标签（如：待补货、常用、淘宝），一个元件可多个标签，与分类互补。
7. **方案份数计算**：可行份数 = min( floor(某元件可用库存 ÷ 该方案单位用量) )，对方案中所有元件取最小值。
8. **购买链接**：单个元件 1 条主链接（备注里可补充其他渠道）。
9. **部署形态**：本机或家庭内网运行（Bun 单进程同时服务 API 与前端静态文件），不做多端同步。

### 1.4 已确认决策（2026-10-08 确认）

1. **数据迁入/迁出**：支持 CSV 格式导入导出（不提供模板，导入按表头字段名自动识别，导出表头即天然模板）；另提供 JSON 备份导出 + 导入恢复。CSV 仅覆盖元件数据（不含图片与方案）。
2. **安装形态**：不做 PWA，普通网页访问。
3. **删除保护**：元件删除采用回收站（软删除，30 天后自动清理，可还原）。
4. **部署环境**：仅家庭内网（HTTP，监听 `0.0.0.0`），无 HTTPS / 防爆破要求。

### 1.5 明确不做（避免过度设计）

多用户/权限、注册流程、i18n、实时协同、全文搜索引擎、PWA、服务端渲染——单用户个人工具均不需要。测试策略：仅对核心计算（可行份数、缺料、单价折算）写少量单测，其余以手测验收。

### 1.6 开放问题（不阻塞开发，默认按 1.3 假设执行）

- 是否需要「入库/出库必须填原因」的强流水？（默认 P1 弱流水）
- 是否需要低库存阈值自动提醒？（默认 P2，先靠方案缺料清单 + 标签「待补货」）

## 2. 技术方案

### 2.1 技术栈

| 层            | 选型                                          | 理由                                                                                                                |
| ------------- | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 前端          | React 18 + TypeScript + Vite                  | 指定                                                                                                                |
| UI 组件       | Ant Design 5                                  | 表格/表单/弹窗开箱即用；内置 `theme.darkAlgorithm`/`defaultAlgorithm` 支持明暗主题切换，Design Token 可全局收紧间距 |
| 数据请求      | TanStack Query                                | 缓存、失效刷新，配合 CRUD 很省事                                                                                    |
| 路由          | React Router v7                               | 标准选择                                                                                                            |
| 运行时/包管理 | Bun                                           | 指定，同时承担 dev server、构建、生产运行                                                                           |
| 后端框架      | Hono（跑在 Bun 上）                           | 轻量、TS 优先、中间件生态（JWT、CORS、静态文件）够用                                                                |
| 数据库        | SQLite（`bun:sqlite` + Drizzle ORM）          | 指定 SQLite；Drizzle 提供类型安全与迁移，驱动直接用内置 `bun:sqlite`，零原生编译                                    |
| 认证          | HTTP-Only Cookie + 签名 Session（HMAC）或 JWT | 单用户，简单安全；密码哈希用内置 `Bun.password`（bcrypt/argon2）                                                    |
| 图片上传      | Hono multipart → 写入 `uploads/`，静态托管    | 简单可靠                                                                                                            |

## 3. 数据库设计

```sql
-- 用户（单行）
CREATE TABLE users (
  id            INTEGER PRIMARY KEY,
  username      TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);

-- 元件分类
CREATE TABLE categories (
  id         INTEGER PRIMARY KEY,
  name       TEXT NOT NULL UNIQUE,      -- 如：MCU / 开关 / 电容
  sort_order INTEGER NOT NULL DEFAULT 0,
  created_at TEXT NOT NULL
);

-- 标签
CREATE TABLE tags (
  id   INTEGER PRIMARY KEY,
  name TEXT NOT NULL UNIQUE
);

-- 元件
CREATE TABLE components (
  id           INTEGER PRIMARY KEY,
  name         TEXT NOT NULL,            -- 名称
  category_id  INTEGER REFERENCES categories(id) ON DELETE SET NULL,  -- 类型
  quantity     INTEGER NOT NULL DEFAULT 0 CHECK (quantity >= 0),      -- 数量
  spec         TEXT,                     -- 规格，如 0805 / 1kΩ / MX 红轴
  price        REAL,                     -- 单价（元）
  color        TEXT,                     -- 颜色
  purchase_url TEXT,                     -- 购买链接
  image_path   TEXT,                     -- 图片相对路径
  note         TEXT,                     -- 备注
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL,             -- 修改时间（编辑时自动刷新）
  deleted_at   TEXT                       -- 软删除时间（NULL=正常；回收站功能）
);

-- 元件-标签（多对多）
CREATE TABLE component_tags (
  component_id INTEGER NOT NULL REFERENCES components(id) ON DELETE CASCADE,
  tag_id       INTEGER NOT NULL REFERENCES tags(id) ON DELETE CASCADE,
  PRIMARY KEY (component_id, tag_id)
);

-- 方案
CREATE TABLE plans (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,             -- 如：HHKB 客制化键盘
  description TEXT,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

-- 方案明细：制作 1 份所需元件及数量
CREATE TABLE plan_items (
  id             INTEGER PRIMARY KEY,
  plan_id        INTEGER NOT NULL REFERENCES plans(id) ON DELETE CASCADE,
  component_id   INTEGER NOT NULL REFERENCES components(id) ON DELETE CASCADE,
  quantity_per   INTEGER NOT NULL CHECK (quantity_per > 0),  -- 单份用量
  UNIQUE (plan_id, component_id)
);

-- 库存流水（P1）
CREATE TABLE stock_movements (
  id           INTEGER PRIMARY KEY,
  component_id INTEGER NOT NULL REFERENCES components(id) ON DELETE CASCADE,
  delta        INTEGER NOT NULL,         -- 正=入库，负=出库
  reason       TEXT,                     -- 手动调整 / 方案出库：<方案名>
  plan_id      INTEGER REFERENCES plans(id) ON DELETE SET NULL,
  created_at   TEXT NOT NULL
);
```

索引：`components(category_id)`、`components(name)`（LIKE 查询，量级小可不建 FTS）、`component_tags(tag_id)`、`plan_items(plan_id)`。

### 核心计算逻辑（服务端 `services/plan.ts`）

```
可行份数 feasible = min over plan_items of floor(component.quantity / quantity_per)
                    （任一元件 quantity_per > 0 且库存为 0 时即 0）

目标 copies 份时，对每个明细：
  need    = quantity_per × copies
  shortage = max(0, need - component.quantity)
缺料清单 = 所有 shortage > 0 的明细，附：元件名、现有量、需要量、缺少量、单价、购买链接
方案总价（1 份）    = Σ quantity_per × component.price
方案总价（copies）  = Σ need × component.price
缺料补齐预估花费    = Σ shortage × component.price
```

## 5. 页面设计

| 页面     | 路由          | 内容                                                                                                                                                                                                            |
| -------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 登录     | `/login`      | 账号密码表单                                                                                                                                                                                                    |
| 元件库   | `/components` | 主页面。筛选栏（搜索/分类/标签）+ 表格（缩略图、名称、类型、数量、规格、价格、修改时间）+ 行内快捷加减库存 + 新建/编辑抽屉（含图片上传、标签选择、购买链接）                                                    |
| 统计看板 | `/dashboard`  | 卡片：元件种类数、总数量、总价值；图表：分类数量分布（饼图）、数量最少的元件 Top10（便于发现待补货）；最近修改列表                                                                                              |
| 方案列表 | `/plans`      | 卡片式：方案名、描述、可行份数徽标（如「可做 3 份」）、1 份总价、缺料元件数                                                                                                                                     |
| 方案详情 | `/plans/:id`  | 明细表（元件、单份用量、当前库存、目标份数下的需/缺、小计金额）；顶部「目标份数」输入框实时计算；汇总卡片：1 份总价 / 目标份数总价 / 缺料补齐预估花费；缺料清单按缺少量排序，附购买链接；P1：「按方案出库」按钮 |
| 设置     | `/settings`   | 修改密码                                                                                                                                                                                                        |

交互细节：

- **单价自动折算**：元件新建/编辑表单中，「单价」与「数量+总价」两种录入方式并存——默认填单价；点选「按总价录入」后输入数量与总价，前端实时显示折算后的单价（总价 ÷ 数量，保留两位，可手动覆盖）。行内快捷补货弹窗同理：填「补货数量 + 花费」，确认后自动更新单价为本次采购价。
- **方案总价**：明细表每行显示「单份用量 × 单价 = 小计」；随目标份数实时联动显示目标总价；缺料清单底部汇总「补齐全部缺料预计花费 ≈ ¥N」。
- **购物清单**：缺料清单支持「一键复制为文本」（元件名 + 缺少数量 + 购买链接），直接粘贴到聊天/备忘录去采购。
- 方案详情中修改目标份数用前端本地计算即时反馈，保存/刷新时以服务端 `feasibility` 接口为准。
- 删除元件进回收站；删除有引用的分类需二次确认并提示影响范围；方案删除为物理删除（可重建，价值低）需二次确认。
- 回收站入口：元件库页顶部 Tab（全部 / 回收站），回收站内可还原或彻底删除，列表显示剩余自动清理天数。
- 移动端为一等公民：所有页面需在手机浏览器上正常使用（见下方 UI 规范）。

### 5.1 UI 设计规范（主题 / 配色 / 间距 / 响应式）

**主题切换**

- 明 / 暗两套主题，顶栏提供切换按钮；首次进入跟随系统 `prefers-color-scheme`，用户手动选择后持久化到 localStorage。
- 基于 Ant Design `theme.algorithm` 实现（`defaultAlgorithm` / `darkAlgorithm`），所有颜色取自主题 Token，组件中不硬编码色值，保证两套主题下显示一致。

**配色**

- 只用纯色，禁用渐变：背景、按钮、卡片、徽标、图表配色全部为纯色填充；图表使用固定的纯色色板。
- 主色选中性偏工业感的单色（如蓝或青），状态色（成功/警告/错误）用 Ant Design 默认语义色。

**间距（紧凑风格）**

- 全局 ConfigProvider 收紧：表格 `size="small"`、表单紧凑布局、按钮默认 `small`。
- 页面容器左右内边距 12–16px，卡片内边距 12px，模块间距 12px；整体内外边距原则上不超过 16px，不使用大面积留白。

**响应式布局**

- 断点：<768px 视为移动端。
- 导航：宽屏侧边菜单，窄屏收起为底部 Tab 栏（元件库 / 看板 / 方案 / 设置四个入口）。
- 表格：窄屏下元件列表切换为卡片列表（图片 + 名称 + 数量 + 价格优先，规格/修改时间等次要信息弱化或隐藏），方案明细表同理横向可滚动。
- 表单与抽屉：新建/编辑抽屉在窄屏下全屏展示，字段单列排布。
- 看板图表：窄屏下纵向堆叠，饼图保持等宽自适应。

## 7. 风险与注意事项

1. **数据安全**：SQLite 单文件，`data/` 与 `uploads/` 加入 gitignore；提供 JSON 备份导出/导入恢复（P1），建议定期导出或直接复制 `data/app.db` 备份。
2. **CSV 兼容性**：导出带 UTF-8 BOM，避免 Excel 打开中文乱码；导入容忍常见表头别名（如「名称/品名」「价格/单价」），仅元件数据，不含图片与方案；重复行按「名称+规格」识别，默认跳过，导入后返回成功/跳过/失败计数报告。
3. **并发**：单用户场景，Bun 单进程 + SQLite WAL 模式足够；库存扣减用事务保证（方案出库）。
4. **图片体积**：前端压缩（长边 ≤1280px、JPEG 0.8）后再上传；服务端仍限制单图 ≤ 5MB 并校验 MIME/扩展名白名单。
5. **安全**：所有输入参数校验（Zod）；Cookie HttpOnly；内网 HTTP 明文可接受，但不开放 CORS；若未来要暴露公网，需加反向代理 HTTPS 与登录限速。
6. **删除保护**：元件软删除进回收站（30 天自动清理，服务启动时顺带执行清理任务）；回收站元件不出现在正常列表、统计与方案计算中，但方案明细引用它时提示「该元件已在回收站」。
7. **局域网访问**：生产监听 `0.0.0.0`，启动时打印本机局域网 IP 与端口，方便手机直接访问。
